# Managed Windows desktop indexing

**Release status: staging only.** The VPS remains the default processing path. Desktop offload requires the migration, `SMARTHR_MANAGED_DESKTOP_ENABLED=1`, and an explicit `SMARTHR_MANAGED_DESKTOP_COMPANIES` list. Leave both settings unset in production pending the physical-device acceptance checks below. No rankings, user interface, or logo are changed.

## What runs where

- The VPS saves and owns every original. Only manual recruiter bulk uploads of two to eight saved, searchable CVs are eligible when local upload slots are busy and an enrolled device has recently reported capacity. Single uploads, email import, and public applications stay on the existing path.
- On a company-managed Windows account, the native ONNX worker polls over HTTPS. It has one active batch, requires available CPU cores and memory, receives only the bounded text for its own lease, and keeps CV text in memory. No provider API is used. Phones, tablets, unenrolled desktops, and weaker machines do not take jobs.
- A missed lease can be assigned once to a different eligible device. With no lease result by the job deadline, the VPS falls back to its own batch. The VPS must be reachable to accept uploads and assign work; a desktop cannot take over for an offline VPS.
- The worker signs the result against the lease, pinned model revision, and exact input digest. The VPS validates it and keeps the same index writer, search fields, and ranking. The database owns the queue, so restarting the scheduler does not lose an accepted batch.

## Prepare and enroll a staging device

1. Use a disposable local-mode environment with the pinned MiniLM model already cached and apply `deploy/vps/migrations/20261121_managed_desktop.sql`. Set the flag and only the staging workspace ID. Configure the reverse proxy to supply the verified HTTPS scheme, not a client-provided header.
2. Build the Windows ZIP with `desktop-worker/Build.ps1 -OutputDirectory <new-directory>`. Distribute it through the company software channel with its SHA-256. Use a managed Windows account with a supported Node.js LTS (22 or newer), npm, and access to the pinned model and packages during install. The scheduled task runs with least privilege **while that account is logged on**, not as a Windows service.
3. Using a signed-in administrator session and its CSRF token, call `POST /api/managed-desktop/admin/invites` in the approved workspace. The code expires after 10 minutes and is usable once. Run `Install.ps1 -Origin https://<staging-host>` from the expanded package and enter the code at the private prompt. Credentials are scoped to the enrolled device and protected by Windows DPAPI, as described in the [PowerShell documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/convertfrom-securestring).
4. Check readiness with `GET /api/managed-desktop/admin/workers`. To decommission, first revoke with `DELETE /api/managed-desktop/admin/workers/<worker-id>` and then run `Uninstall.ps1 -RevokedInSmartHR` under the enrolled account.

## Verification and rollout gate

- `tests/test_managed_desktop_pipeline.py` exercises the real database lease and API rules with disposable PostgreSQL. `tests/local-upload-pilot/verify-pipeline.mjs` runs staging bulk uploads, two native agent identities, reassignment, timeout fallback, and search parity with synthetic PDFs. The staging run requires the SSH host and immutable baseline image specified by `PILOT_BASELINE_SSH` and `PILOT_BASELINE_IMAGE`, local pinned assets and npm dependencies, and Python `cryptography`. It mounts candidate code over a cached image, uses an isolated Docker network, and never reads production CVs or the production database.
- In the single-workstation staging run, all 18 PDFs became searchable after one expired lease was reassigned. Another two PDFs indexed through the VPS after the job deadline. Eight searches, including a 10-result request and folder/tag/upload-date filters, returned the same 30 ranked entries. Scores agreed within `1e-5`. The VPS executed zero embedding batches for the 18 offloaded files, compared with three normally. Measured API-process CPU was 387.41 ms versus 425.76 ms (about 9% lower) on that fixture, not a measurement of total VPS load. No paid AI calls were made.
- Two identities on one machine cannot validate independent desktop outages, scheduled-task behavior across logoff/sleep, or capacity on lower-end devices. Before live rollout, run the installed worker on two independently enrolled company devices and repeat an agreed concurrent load test. Compare VPS CPU and upload-to-search latency (including p95), verify that no completed uploads are lost, and require ranking and exact-filter parity. Offload reduces inference work only; it can add wall-clock latency during reassignment or timeout.
- For rollback, stop assigning new work by clearing the enable flag and restarting the app. Keep the migration and scheduler in place while already-saved jobs drain to VPS indexing. Revoke desktop records before uninstalling. Do not drop tables with work in flight or remove source CVs.
